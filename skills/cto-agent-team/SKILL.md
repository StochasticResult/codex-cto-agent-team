# CTO agent team

Coordinate a CTO, five product managers (PMs), and ten engineers (CS) per PM. The CTO assigns work, resolves cross-team dependencies, and delivers the result; each PM scopes and reviews its team's work; engineers execute assigned work and return evidence. Consult `assets/roster.json` for the role definitions.

Treat engineer titles as preferred specialties, not restrictions. Assign suitable independent work in parallel when it shortens delivery. Keep the five teams and requested model settings. Give each item an output, dependencies, acceptance criteria, and one writer per shared resource. Start the next ready item when an engineer finishes, without waiting for a whole wave. Prioritize work that blocks delivery. Do not invent work, duplicate reviews, or repeat passed checks for unchanged inputs. Record a concrete reason when the remaining work must be serial.

Honor the user's task, permissions, and any applicable `AGENTS.md` in the target project. Assign one writer per shared resource, including files, desktops, and applications. The CTO coordinates conflicts across teams. Verify device connectivity, identity, and authorization for the specific task separately.

Before relevant planning, implementation, or review, find suitable guidance in the available skill catalog. Start with explicit user and project direction before generic preferences. Read selected actual content and necessary references, reusing valid same-context evidence. Owners compare the resulting artifact with observable acceptance. A skill label, read command, or passing code tests alone does not prove the required outcome.

For user-facing work, record the primary task for someone using the product for the first time. Use useful defaults and the [usability baseline](references/ui-design.md#usability-baseline) in handoffs, implementation, and artifact acceptance. Record actual observations and limits without claiming universal usability.

Consider Anthropic Frontend Design for applicable frontend work. Choose it, `emil-design-eng`, or both by task, rather than using a fixed Emil priority. Read [ui-design.md](references/ui-design.md) for selection and handoff requirements. Read the actual selected skills and applicable references. Preserve user requirements, the existing design system, and accessibility. Record decisions privately. Apply this to unfinished work without restarting accepted UI or adding repeated release gates.

Use the core `ponytail` skill from [DietrichGebert/ponytail](https://github.com/DietrichGebert/ponytail) for coding, fixes, refactoring, dependency choices, and code review by any team role. Read the actual skill with `full` as the default guidance level and [coding.md](references/coding.md) for this team's integration boundaries. Include this reading requirement in each applicable new or resumed agent handoff. Reuse valid reading evidence within the same context. Choose the smallest complete solution while preserving required quality and user scope. Combine Ponytail with the selected UI guidance when applicable. Skill levels do not change model or reasoning settings.

Use applicable Superpowers modules for a real task need, such as `systematic-debugging` for fault investigation and `verification-before-completion` for scoped evidence. Read [coding.md](references/coding.md) for availability and compatibility boundaries. Existing authorization and project rules govern. Do not add blanket approval gates, mandatory worktrees, extra agent trees, repeated full-suite checks, or per-reply and heartbeat loading.

Write English PM task instructions, engineer handoffs, and questions for other people with the official ASD-STE100 writing rules and dictionary. Read [handoffs.md](references/handoffs.md) before drafting or checking this text. Use the source issue and a documented technical-term review, not a short-sentence substitute. Keep Chinese user summaries clear, without a claim of English-standard compliance. Distinguish a draft, a checked text, and verified compliance. State missing checks and review limits.

Choose the model and reasoning level by task. Default coordination and research to `gpt-6.1-sol` / `high`, scoped engineering to `gpt-6.1-terra` / `high`, simple extraction to `gpt-6.1-terra` / `medium`, and complex engineering or critical review to `gpt-6.1-sol` / `xhigh`. Read [model-routing.md](references/model-routing.md) before dispatch. Honor user overrides and approved escalation scope. Role defaults do not establish a chat's actual configuration. Apply routes on the next authorized dispatch. Keep active work and the CTO's current settings intact.

Delegate routine mechanical supervision to a suitable agent using `gpt-6-luna` / `low` within the approved scope. Keep the CTO focused on intake, assignment, cross-team decisions, and final delivery. Verify supported monitor settings before claiming this route is applied. A model name in a prompt is not a model setting. Keep unchanged checks quiet; route actionable failures and completed-result evidence for substantive acceptance.

Recover confirmed temporary model-capacity failures without asking the user to retry. The CTO owns PM recovery, and each PM owns recovery for its own engineers. Preserve the failed turn's recorded model and reasoning level. Current route defaults do not replace that configuration. Read [recovery.md](references/recovery.md) before a retry. Inspect current task and turn state, keep delayed retries and uncertain-send records private, and resume unfinished work in the same chat. Do not restart active work or repeat completed effects. Keep ordinary retries quiet.

User authorization for internal delegation and message forwarding is required; reuse prior explicit authorization. Skill selection alone does not authorize creation of independent chats. Create independent chats only when the user requests them; preferentially reuse verified existing chats. For a general request for agents, use collaboration only when authorized and available, or plan the work first. Read [workflow.md](references/workflow.md) when establishing or operating the team, dispatching, or collecting results.

Keep the CTO chat available for new requests. Give each independent request a unique private task record, goal, acceptance criteria, and owning PM. Dispatch a complete handoff, briefly acknowledge the start, and end the CTO turn without waiting for implementation. PMs continue through implementation, review, and authorized delivery in their own chats. Preserve every open task when new requests arrive; attach changes or cancellations to the original task. Coordinate shared resources before parallel work.

Keep detailed progress in PM chats and notify the user briefly when a result is ready, or when a failure needs their action. When completion follow-up is requested, use an available, authorized thread heartbeat or automation for the supervisor. Reuse existing monitoring instead of adding routine CTO polling. Save cursors and notification state privately. Verify the result before notifying, and retire a one-time monitor only when all its duties are complete. If monitoring is unavailable, explain the limit instead of implying that an ended turn will wake itself. The workflow reference describes handoffs and notification recovery; the state helper does not implement scheduling.

Keep actual chat and host identifiers, task and notification records, runtime evidence, and local paths in a private state directory outside both the public repository and the installed skill directory. Never put credentials in state; use credential references. Read [state.md](references/state.md) when initializing, registering, or validating private state. A roster defines roles; it does not establish real chats, readiness, or active execution.

Use completed-task or recurring-failure events to record bounded improvements. Read [workflow.md](references/workflow.md#evidence-based-improvement) for observation, validation, adoption, trial, and rollback. Keep unknown costs unknown. For another project or machine, follow [portable setup and resume](references/state.md#portable-setup-and-resume). Check needed capabilities and any required credentials or device permissions. Reuse valid authorization. Copied state cannot grant it.
