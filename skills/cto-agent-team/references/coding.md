# Ponytail for coding and review

Use the core `ponytail` skill for coding, fixes, refactoring, dependency decisions, and code review. Find it through the current skill catalog and read its actual content. The [upstream core skill](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md) is the reference. This routing guide does not replace it. Use `full` guidance by default. `lite`, `full`, and `ultra` describe skill behavior, not model reasoning or speed settings.

This applies to the CTO, every PM, and every engineer when doing applicable work. New or resumed agent handoffs must include the actual core skill reading requirement for that work. Read it once per relevant context; reuse recorded source/version evidence and reread only when needed or the source changes. An installation or role reference does not prove a particular chat has read it. Keep all roles focused on useful reuse, complete outcomes, concise results, and necessary tool calls. Mechanical supervisors need not reload the skill on each tick or perform code review.

Trace the affected behavior and callers before choosing a change. Prefer the project's existing components and helpers, standard platform capabilities, and installed dependencies. Deliver the complete requested behavior with the least unnecessary complexity. Preserve required validation, error handling, security, accessibility, data integrity, hardware calibration, and meaningful tests. Keep checks proportional and reuse successful evidence for unchanged inputs. Do not turn this preference into recurring whole-repository audits or optional abstractions.

For UI coding, select [the applicable UI guidance](ui-design.md) alongside Ponytail. Consider Frontend Design and choose it, Emil, or both by task. Design guidance informs the interface, while Ponytail reduces unnecessary implementation. Neither changes authorization, model settings, resource ownership, ASD-STE100 handoffs, rapid intake, useful parallel work, or completion follow-up. Honor later user overrides.

## Task-specific workflow modules

Consider applicable [Superpowers](https://github.com/obra/superpowers/tree/2ce8aa15d05bd57213e6f746f953aafb7ded7a8b/skills) modules after checking their actual availability. The reviewed source is version 7.0.1, under the MIT license. Read the selected module and only its relevant references. Installing this CTO skill does not install the suite, its host plugins, or its runtime tools.

| Module | Use |
| --- | --- |
| `systematic-debugging` | Investigate a reproducible bug, failing test, or unexpected behavior. Trace causes, compare working cases, test one hypothesis, and verify the scoped fix. |
| `verification-before-completion` | Identify evidence for a completion claim, run the affected checks, and inspect the result before reporting success. |

Apply current project rules and the user's authorization before upstream workflow defaults. Preserve existing acceptance and valid evidence for unchanged inputs. Do not turn these modules into blanket approval gates, mandatory worktrees, extra agent trees, repeated full-suite checks, or per-reply loading. An engineer does not acquire delegation authority from a module. Reuse the existing writer, chats, and installation owner. Host-specific hooks, tools, scripts, and plugin namespaces need separate verification before use. Do not run companion servers, telemetry, session scans, or installers merely because a reference mentions them.

Keep source/version, applicable guidance, compatibility differences, and review limits privately. No module expands permissions for publication, external messages, devices, purchases, or model changes. A software test or a file check does not by itself establish business acceptance.

A standalone core skill can supply the guidance without a host-specific plugin. Discover or install it through the available authorized skill workflow, reusing any existing installation owner. Do not make Claude Code dashboards, hooks, session-log import, telemetry, slash commands, or token reporting prerequisites. Report only capabilities actually installed and tested. Keep source/version and installation evidence private.

Keep the user's short CTO summaries. Include material unchecked behavior or risks where relevant. This user preference takes precedence over routine per-message boilerplate. Do not present the upstream author's benchmark percentages as this team's measured token, time, or cost savings. No local savings claim follows merely from installation.

## Consumer-contract evidence

When a JSON, CLI, API, storage, or cross-language boundary changes, identify its actual consumer. Keep a scoped local fixture for that consumer's accepted schema or request, with the source and version. Include a meaningful negative case. A same-named tool in another environment is not a substitute contract. Keep the check local when possible. Do not send empty business messages, run model probes, or add tests for unchanged boundaries merely to produce evidence.
