# Default UI design skill

Use `emil-design-eng` by default for UI design, component implementation, interaction design, visual polish, and UI review. The [upstream repository](https://github.com/emilkowalski/skills) identifies it as the main skill. Honor a later user override. Pure backend or unrelated research work does not require a design step.

Find the skill in the current environment's skill catalog. Read its actual `SKILL.md` and only the references relevant to the task. Resolve references through that skill's own provider or directory. Do not assume a machine-specific path or embed third-party skill text here. If the dependency is absent, use the available skill-installer workflow within the user's authorization. State an access or installation failure and its effect accurately. Do not claim the skill was read when it was unavailable.

Give the assigned engineer the UI goal, target component or view, product constraints, existing design system, expected interaction, and acceptance criteria. Require actual application of the skill, rather than a name in the handoff. Keep evidence in private task records: the source/version read where available, applicable sections, concrete choices, reasons, and validation limits.

Useful decisions include whether motion serves a real interaction, how feedback preserves task speed, and how keyboard, focus, reduced-motion, touch, and narrow-screen behavior remain usable. Preserve the current design system and user requirements. Add motion only for a useful purpose. Do not automatically apply every animation technique or load every skill from the upstream collection. Other skills retain their own applicability and explicit-invocation rules.

For a UI code review, follow the actual skill's required review format, including its Before/After/Why table. Tie findings to observed interface behavior and scoped source. Do not invent issues to fill the table. A real accessibility or behavior failure justifies a targeted correction and affected checks. A preference alone does not justify repeating completed work, unchanged tests, or release review.

Apply this default to unfinished UI work. Keep accepted candidates moving through the existing release path. Record any concrete design issue that changes readiness, rather than adding a general design approval gate. Model settings, resource ownership, action permissions, ASD-STE100 handoffs, and completion-notification rules remain unchanged.

For UI implementation and code review, also use [the core Ponytail coding guidance](coding.md). It governs unnecessary code complexity while Emil remains the design preference. Preserve both the requested interface behavior and the required quality checks.
